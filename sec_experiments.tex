\section{Computational Experiments}
\label{sec:results}

The purpose of the experiments is not to establish optimality. For
procurement transport planning at an operational level, what matters
is whether a procedure returns, in a usable amount of time, a plan
that a loading crew can actually execute and that improves on what
the company does today. The experiments are organised around those
two questions, and a third that turns out to dominate both: whether a
model that abstracts the loading geometry away produces plans that
can be executed at all.

\subsection{Protocol and declared budgets}
\label{sec:protocol}

All calculations use Python. The restricted master, the aggregate
integer master and the partition MIPs of the construction, the
volumetric benchmark and the compact models are solved with Gurobi
12; the pricing subproblem
\eqref{eq:PPObjective}--\eqref{eq:PPsymm} and the placeability tests
with CP-SAT from OR-Tools 9.12. The machine on which each run was
made is recorded with the run and reported with the tables
(\pending{host and core count of the regenerated campaign}).

\paragraph{Every row carries its configuration.}
Five parameters can change the answer a solver returns, and every run
records all five with its result: the wall-clock \emph{time limit};
the relative \emph{MIP gap} at which an integer solve is allowed to
stop; the \emph{thread count}; the \emph{memory cap} per model; and
the random \emph{seed}. Table~\ref{tab:protocol} states the values
under which each stage of the study is run. A row whose configuration
is not recorded is not reported: an earlier set of fleet-tree runs was
discarded on exactly that ground, since nothing tied them to a budget.

\paragraph{Memory is a budget, not an accident.}
Gurobi holds its branch-and-bound tree in memory and imposes no limit
of its own, so a compact model whose dual bound has stalled simply
grows its list of unexplored nodes until the machine intervenes. We
therefore give every model an explicit per-model soft memory limit,
at which the solver stops and returns its incumbent and its dual bound
with the status \textsc{mem\_limit}, exactly as a time limit would.
Two consequences follow for how the results may be read. A solve that
stopped on memory is a solve that stopped, and its dual bound is a
valid lower bound on the model's optimum regardless of why it stopped.
And reaching a fixed per-model cap sooner on a larger model is a
statement about the cap, not about tractability; we draw no inference
from \emph{when} the cap was reached, and the cap is reported as a
parameter of the experiment like the time limit.

\paragraph{What each reported quantity means.}
\begin{itemize}
\item $z$ is the cost \eqref{eq:MPObjective} of the plan returned,
  net of any artificial penalty; a plan is reported only if it carries
  no artificial slack. For the fleet tree and MATH-3D-SCPTOP it is the
  incumbent of Algorithm~\ref{alg:bp3d}; for the compact models it is
  the solver's incumbent at its stop. It is an upper bound on the
  optimum in every case.
\item \emph{trucks} is $\sum_{g,t}n_{gt}$ for that plan.
\item $\mathrm{LB}$ is a lower bound on the optimum of the model the
  method solves. For the tree it is the \emph{certified} bound of
  Section~\ref{sec:bounds}: the root certificate, or the minimum over
  the certified bounds of the open frontier when that is higher. A
  \emph{root proved} flag records whether the root sweep returned
  every pair proved; without it no bound is printed. For a compact
  model it is the solver's dual bound at its stop.
\item \emph{gap} is $(z-\mathrm{LB})/z$ against the method's own
  bound. It is an optimality gap only where the bound is certified; it
  is never a gap to a proven optimum unless the row says
  \emph{proved}.
\item \emph{stop} names the condition under which a solve ended:
  \textsc{optimal}, \textsc{time\_limit} or \textsc{mem\_limit}. A time
  or memory stop makes the row's time the budget rather than a solve
  time.
\item \emph{nodes}, \emph{open}, \emph{columns} (priced / built) and
  the time split between column generation, the aggregate master, the
  partitions and the integer master describe the tree. \emph{open} is
  the number of regions left unexpanded when time ran out; a run with
  open regions has not searched the space, whatever its gap.
\item \emph{loadable} is the outcome of re-verifying every dispatched
  truck of a plan against \eqref{eq:col-geom}--\eqref{eq:col-agg} by a
  routine that shares no code with the solver that produced it.
  \emph{unloadable} counts, among the loads a volumetric plan
  dispatches, those a constraint programme has \emph{proved} cannot be
  stacked and placed in a trailer; loads the programme could not decide
  within its limit are reported separately as \emph{undecided} and are
  counted neither way.
\item $\Delta z$ is the cost of one method relative to another on the
  same instance, and is meaningful only between plans both of which
  are loadable.
\end{itemize}

\subsection{Instance generation}

Thirty-six benchmark instances are generated as a full factorial over
the four explanatory variables of the study: the number of products
$|N|\in\{4,8\}$, the horizon $|T|\in\{5,10\}$, the number of RTI
types $|R|\in\{2,3,4\}$ and the volumetric granularity
$v\in\{60,90,120\}$. Instances are named $I\_|N|\_|T|\_|R|\_v$.

\begin{itemize}
  \item \textbf{Container dimensions}: footprints are drawn from the
  industrial catalogue $\{1200\times800,\;1200\times1000,\;
  800\times600,\;1200\times1600,\;2400\times1200\}$ mm. Heights are
  quantised to $50$ mm and a footprint is admissible for a given $v$
  only if the implied erected height lies in $[400,1500]$ mm, so that
  an RTI is worth stacking and at least two layers fit under the
  trailer roof. Whenever $|R|\ge3$ several RTI types share a
  footprint, reproducing a real catalogue in which container families
  sit on a common pallet base; this is what allows a stack to mix
  types across layers.

  \item \textbf{Container volume}: $v$ is the number of erected RTIs
  that fill one truck by volume, and every RTI type is generated with
  volume at least $\Gamma_{K}/v$. Larger $v$ means smaller RTIs and a
  harder placement subproblem.

  \item \textbf{Demand}: generated per product and period by deviating
  $\pm10\%$ from a mean calibrated so that roughly $2.5$ truckloads
  are consumed per period. Calibrating the mean keeps difficulty
  comparable across the factorial instead of letting it drift with the
  RTI size.

  \item \textbf{Weights}: the content weight of a full RTI scales with
  its volume and varies by $\pm25\%$ between products sharing an RTI
  type, which is what makes the per-stack crush limit depend on the
  period's product mix rather than on the RTI type alone.
\end{itemize}

The truck is a standard semi-trailer,
$pK\times qK\times rK=13600\times2400\times3000$ mm, payload
$pK^{w}=24$ t, per-stack crush limit $W^{\max}=1200$ kg, minimum
utilisation $\alpha=0.55$ and cost $cK=1000$ per dispatch. Lead time
is $lt=1$ and coverage stock one period of demand.

\paragraph{A size ladder.}
The benchmark tops out at $|N|=8$ and $|T|=10$. To find where, if
anywhere, the decomposition pays against the compact model, a second
set of instances is generated with the same rules along two axes:
$(|N|,|T|)\in\{(8,10),(12,12),(16,15),(24,20),(32,20)\}$, and the
number of truckloads consumed per period, $2.5$, $5$ or $8$, which
scales the fleet $K$ and with it the number of interchangeable trucks
the compact model indexes. These instances have $|R|=2$ and $v=90$ and
are named $I\_|N|\_|T|\_2\_90\_k$ followed by ten times the truckloads
per period. They stress different things: $|N|$ and $|T|$ grow the
master and the number of pricing calls, while the fleet grows the
compact model's per-truck variables and its symmetry.

\paragraph{Sizing the RTI fleet.}
One generation parameter deserves comment because it is easy to get
wrong and the symptom is misleading. Empties return by the truckload,
and a return truck leaves only once the plant has accumulated enough
folded RTIs to clear the full-truckload floor. Since folded RTIs pack
very densely, that takes several periods, during which the supplier
must live off its own folded stock. If the fleet is sized only for the
lead time, the linear relaxation remains feasible by dispatching
fractional trucks while the integer problem has no solution at all.
We therefore size the supplier's initial folded stock of each type to
cover $lt+SC$ periods plus the number of periods, capped at six,
needed to accumulate $\lceil\alpha\Gamma_{K}/\gamma_{sr}\rceil$
folded RTIs at the plant's rate of emptying them, which is the
standard closed-loop argument that an RTI fleet must cover the cycle
time.

\subsection{Methods compared}

\begin{itemize}
\item \textbf{Fleet tree} --- Algorithm \ref{alg:bp3d} on the
      Dantzig--Wolfe master over the volumetric oracle of
      Section~\ref{sec:pp}, certified at the root and at the region
      $X\le X^{\star}-1$. This is the configuration under which the
      size ladder is run, since it is where per-node certification is
      affordable.
\item \textbf{Compact SCPTOP reference} --- the volumetric model of
      Appendix~\ref{appendix:A} solved directly by Gurobi, under the
      declared budgets of Table~\ref{tab:protocol}. It solves the same
      problem as the fleet tree row above, so the two bracket a common
      optimum.
\item \textbf{MATH-3D-SCPTOP} --- Algorithm \ref{alg:bp3d} with the
      constraint programming oracle, on the benchmark instances. The
      construction's step 3 is volumetric there
      (Section~\ref{sec:wip3d}), so its plans are those of the
      integer master over priced columns and of partitions that
      passed placeability; every dispatched truck is verified.
\item \textbf{Company procedure (PLC-SCPTOP)} --- the master problem
      over a fixed pool of manually derived loading configurations,
      one regular grid per container type, as produced today by a
      spreadsheet.
\item \textbf{SCPTOP} --- the volumetric benchmark of Appendix
      \ref{appendix:A}, identical to the master in every respect
      \emph{except} that truck capacity is volumetric. The comparison
      therefore isolates the effect of the loading representation.
\item \textbf{Compact 3D-SCPTOP} --- solved directly, on the small
      instances where that is still possible, warm-started with the
      matheuristic's plan.
\end{itemize}

Every truck that a geometric method dispatches is re-verified from
scratch against \eqref{eq:col-geom}--\eqref{eq:col-agg} by a routine
that shares no code with the solver that produced it. Every truck
that SCPTOP dispatches is submitted to an independent constraint
programme asking whether that exact set of RTIs can be stacked and
placed in a trailer at all, with the slot bound \eqref{sb:eq:Ibound}
in force so that an infeasibility verdict is a proof.

\subsection{Discussion}

\paragraph{Bracketing the volumetric optimum.}
On the size ladder the fleet tree and the compact SCPTOP model solve
the same problem, and each returns a verified plan and a valid lower
bound. Neither proves optimality: the compact model stops on its
memory cap on every ladder instance, and the tree closes none of its
open regions. What can be stated is a \emph{bracket}: the optimum lies
between the higher of the two lower bounds and the lower of the two
plan costs. On the three largest instances of the ladder ---
$I\_16\_15\_2\_90\_k50$, $I\_24\_20\_2\_90\_k50$ and
$I\_24\_20\_2\_90\_k80$ --- the compact model's dual bound at its
memory stop lies \emph{below} the tree's certified root bound, so the
Dantzig--Wolfe certificate is the lower end of the bracket there; on
the two smallest the compact model's bound at its stop is the higher
of the two. Table~\ref{tab:fleet} reports the values, the stop
condition of every compact solve, and the number of regions the tree
left open.

\paragraph{What the tree does not deliver.}
In every recorded run the tree's global bound equals its root bound:
no open region was certified to a value above the root, and no run
satisfied the conditions under which Algorithm~\ref{alg:bp3d} claims a
proof. The tree therefore closed no gap in these experiments. What it
did is documented by the columns it built: the incumbents come from
constructions inside regions the root never examined, and the gaps
reported are gaps to a root certificate, not to an optimum. We report
them as such.

\paragraph{A volumetric capacity is not a conservative approximation.}
The loads that SCPTOP dispatches are each submitted to a placeability
proof. The share proved impossible to place, by instance factor, is
reported in Table~\ref{tab:summary}, together with the share left
undecided, which must be read alongside it: a zero count of proven
infeasibilities means nothing if most loads were undecided. The
direction of the error is what the comparison is designed to expose.
A volumetric capacity ignores the remainders that footprints and layer
heights leave unusable, so where it errs it errs by dispatching loads
that do not fit, and a planner handed such a plan discovers the
shortfall on the loading dock. Whether that error concentrates on the
coarse containers, as the geometry suggests it should, is a reading of
Table~\ref{tab:summary} and is left to the regenerated table.

\paragraph{Feasibility by construction.}
Every plan the geometric method returns is re-verified truck by truck
against \eqref{eq:col-geom}--\eqref{eq:col-agg} by code that shares
nothing with the solver that produced it, and the \emph{loadable}
column of Table~\ref{tab:main} records the outcome for every row. That
is a property of the formulation rather than of the search: a column
is a witnessed layout, so a plan assembled from columns is executable
by construction and can be handed to a loading crew as a drawing. The
realised utilisation of the least-filled truck in each plan is
reported with the table.

\paragraph{Against the procedure in use.}
The case study of Section~\ref{sec:case} compares the same machinery
against the company's average-mix configurations and against a richer
hand-drawn set. Its table is pending regeneration with the current
code and with the baselines solved to the same gap as the method, and
no percentage from the previous revision is repeated here.

\paragraph{Pricing technology.}
The subproblem was solved both as a constraint programme and as a MILP
with the big-$M$ non-overlap encoding
\eqref{sb:eq:nonov-x1}--\eqref{sb:eq:nonov-y2}, by running the whole
method with each backend on the same instances under identical
budgets (Table~\ref{tab:oracle}). The comparison is valid only because
both oracles now solve the same problem: an earlier version of the
MILP oracle imposed the full-truckload requirement as the sum of the
two ratios rather than as the disjunction \eqref{eq:col-truck}, solved
a strictly weaker problem, and produced a column that failed
verification, so the advantage it appeared to show was an artefact.
Which technology is used for the geometric rows, and on what evidence,
is stated with the regenerated table.

\paragraph{Where each method belongs.}
Table~\ref{tab:exact} sets the compact 3D-SCPTOP model against the
matheuristic on the small instances, both under the same wall-clock
budget and the compact model warm-started with the matheuristic's
plan. The reading we expect, and will state only where the table
supports it, is that the crossover is the planning horizon and the
fleet rather than the raw size of the formulation: where the compact
model closes an instance it remains the better tool, and the case for
the decomposition rests on the regime beyond that, where the compact
model's tree grows to its memory budget with a stalled bound while the
decomposition returns a verified plan and a certified bound. The size
ladder is where that regime is measured.
